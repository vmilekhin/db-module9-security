# Модуль 9. Безопасность баз данных (PostgreSQL 18)

## Лабораторная работа: Модель угроз и границы доверия

В ходе работы была создана учебная среда для проверки механизмов защиты PostgreSQL: ролей, прав доступа (GRANT), Row Level Security (RLS) и TLS.

### 1. Активы и субъекты
*   **Актив:** Данные таблицы `app_schema.orders` (информация о заказах разных арендаторов).
*   **Субъекты:** 
    *   `owner_role` (владелец таблицы).
    *   `app_rw` (роль приложения с правами чтения/записи).
    *   `analyst_ro` (роль аналитика с правами только на чтение).
    *   `tenant_a` и `tenant_b` (роли конечных пользователей-арендаторов).

### 2. Результаты негативных тестов (Разграничение прав)
*   **Тест 1:** Попытка `analyst_ro` удалить данные (`DELETE`).
    *   *Результат:* `ERROR: permission denied for table orders`. Права разграничены корректно.
*   **Тест 2:** Попытка `app_rw` создать новую таблицу.
    *   *Результат:* `ERROR: permission denied for schema app_schema`. Роль приложения ограничена в изменении структуры БД (принцип минимальных привилегий).

### 3. Проверка Row Level Security (RLS)
Была включена политика `tenant_isolation`, сравнивающая `tenant_id` в строке с переменной сессии `app.current_tenant`.
*   При установке контекста `tenant_a` роль `app_rw` видит только 2 строки (свои).
*   При установке контекста `tenant_b` роль `app_rw` видит другие 2 строки.

### 4. Атака на архитектуру (Главный вывод)
**Проблема:** В реальных приложениях часто используется одна общая роль (`app_rw`) для всех пользователей. Если злоумышленник сможет повлиять на переменную `app.current_tenant` (например, через SQL-инъекцию в приложении), защита RLS будет обойдена.
*   *Эксперимент:* Находясь под ролью `app_rw`, мы успешно переключили контекст с `tenant_a` на `tenant_b` и увидели чужие данные.
*   *Вывод:* RLS не является барьером, если граница доверия (приложение) скомпрометирована, и клиент может управлять контекстом сессии. Требуется доверенная передача идентификатора пользователя (например, через JWT на бэкенде).

### 5. Проверка TLS
Команда `SELECT * FROM pg_stat_ssl` показала `ssl = f` (false), так как подключение осуществляется через локальный unix-socket. В production для защиты канала от прослушивания (MITM) необходимо использовать параметр `sslmode=verify-full` в строке подключения.
